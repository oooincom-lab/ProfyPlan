# ТЗ 1.5 для 1С AI: заказ-наряды, CCM/M:N и связи «операция ↔ ресурс»

**Дата:** 26.10.2026  
**Адресат:** разработчик расширения 1С  
**Основание:** ТЗ 1.4, решения ProfyPlan от 25–26.10.2026  
**Статус:** дополнение к `1c-tz-1.4.md`; обратная совместимость с `profyplan.exchange.v1` сохраняется

## 1. Зачем это дополнение

Пилот запускается вместе с CCM. Для CCM недостаточно передать заказ, номенклатуру и «Ресурсы предприятия» на уровне заказа: ProfyPlan должен понимать, **какая операция выполняется каким ресурсом**, сколько ресурса она занимает и какие ресурсы являются основными, альтернативными или вспомогательными.

Одновременно в обмен добавляется **заказ-наряд** — документ, где номенклатура имеет вид работы, а исполнителями являются люди и бригады. Текущий `orders` принимает только `production_order`, поэтому заказ-наряд сейчас отбрасывается.

Цель дополнения:

- принимать заказ-наряды как отдельный тип планируемого заказа;
- принимать людей и бригады как ресурсы, а не как оборудование;
- получать явную M:N-связь «операция ↔ ресурс»;
- обеспечивать корректный CCM: один основной ресурс на производственную операцию, альтернативы и помощники — по правилам;
- давать пользователю понятную проверку покрытия операций ресурсами и удобное исправление.

## 2. Главные решения

1. **1С остаётся ведущей системой** для справочников, заказов, операций, ресурсов и фактов.
2. **Спецификации как справочник ProfyPlan не используются.** Операции, ресурсы, подразделения и длительности берутся из заказа на производство или заказ-наряда.
3. **Заказ-наряд — отдельный тип `work_order`.** В модели 1С это `Документ.ЗаказПокупателя` с `ВидОперации = ВидыОперацийЗаказПокупателя.ЗаказНаряд` (форма `ФормаЗаказНаряда`), если в конкретной конфигурации нет отдельного документа. Точное имя объекта подтвердить по метаданным.
4. **Связь «операция ↔ ресурс» — many-to-many.** Одна операция может использовать несколько ресурсов; один ресурс может участвовать в нескольких операциях.
5. **Для CCM у каждой производственной операции должен быть ровно один `primary`-ресурс.** Альтернативные ресурсы — варианты замены, а не одновременная загрузка. Вспомогательные ресурсы (`helper`) могут добавляться к основной операции.
6. **Структурная единица и этап не являются ключом связи.** Связь задаётся явно через `operation_uid + resource_uid`; эвристика по подразделению/этапу допустима только как подсказка, но не как единственный ключ.
7. **Сотрудники и бригады — не оборудование.** Для них используются `employee`/`org_unit` и ресурсные профили `employee`/`team`.
8. **Без явной связи CCM не считается корректным.** CPM может работать без ресурсов; CCM — нет.

## 3. Термины

| Термин | Смысл |
|---|---|
| `production_order` | Заказ на производство |
| `work_order` | Заказ-наряд: работы, люди, бригады |
| `operation_uid` | Стабильный UID строки операции |
| `resource_uid` | UID ресурса: человек, бригада, оборудование, рабочее место |
| `primary` | Основной ресурс операции; определяет длительность/загрузку |
| `alternative` | Возможная замена; не занимает ресурс одновременно с primary |
| `helper` | Вспомогательный ресурс, занятый вместе с primary |
| `capacity_demand` | Сколько единиц ресурса требует операция |
| `resource_type` | `employee`, `team`, `equipment`, `workplace` |

## 4. Целевая модель заказ-наряда

### 4.1. Шапка `work_order`

| Поле | Обязательность | Комментарий |
|---|---|---|
| `uid` | да | UID документа 1С |
| `order_type` | да | строго `work_order` |
| `number` | да | номер документа |
| `date` | да | дата документа |
| `organization_uid` | да | организация |
| `customer_uid` | да | заказчик, если есть |
| `project_uid` | нет | проект ProfyPlan, если уже связан |
| `parent_production_order_uid` | нет | родительский заказ на производство, если заказ-наряд выпущен по нему |
| `status` | да | статус документа 1С |
| `comment` | нет | комментарий |
| `version` | да | версия из регистра версий |
| `updated_at` | да | время версии |

### 4.2. Строки работ

| Поле | Обязательность | Комментарий |
|---|---|---|
| `line_uid` | да | стабильный UID строки |
| `nomenclature_uid` | да | номенклатура |
| `work_type_uid` | желательно | вид работы, если есть отдельный справочник |
| `work_type_name` | да, если нет UID | человекочитаемый вид работы |
| `quantity` | да | количество |
| `unit_uid` | да | единица измерения |
| `department_uid` | нет | подразделение выполнения |
| `stage_uid` | нет | этап |
| `price` | нет | цена, если нужна для отчётности |

Номенклатура работ передаётся с `ntype = "service"`. Если в 1С есть отдельный вид работы, он передаётся в `work_type_uid/name`, а не подменяется именем номенклатуры.

### 4.3. Операции заказ-наряда

| Поле | Обязательность | Комментарий |
|---|---|---|
| `operation_uid` | да | стабильный UID строки операции |
| `source_line_uid` | желательно | строка работы, к которой относится операция |
| `sequence` | да | порядок внутри заказа/строки |
| `operation_name` | да, если нет UID | имя операции |
| `duration_hours` | да для планирования | десятичные часы |
| `setup_hours` | нет | подготовительно-заключительное время |
| `quantity` | нет | объём операции |
| `department_uid` | нет | подразделение |
| `stage_uid` | нет | этап |
| `executor_uid` | нет | исполнитель, если задан на операции |
| `executor_type` | нет | `employee` или `org_unit` |

Если строки операций не имеют UID, в расширении нужно добавить `ПФП_UIDОперации` и заполнять его стабильно. `КлючСвязи` продукции и `НомерСтроки` не заменяют UID: при перезаписи строки связь с ресурсами потеряется.

### 4.4. Связь операции с ресурсом

| Поле | Обязательность | Комментарий |
|---|---|---|
| `order_uid` | да | заказ, к которому относится связь |
| `order_type` | да | `production_order` или `work_order` |
| `operation_uid` | да | операция |
| `resource_uid` | да | ресурс |
| `resource_type` | да | `employee`, `team`, `equipment`, `workplace` |
| `role` | да | `primary`, `alternative`, `helper` |
| `capacity_demand` | да | количество единиц ресурса, обычно `1` |
| `duration_override_hours` | нет | переопределение длительности |
| `efficiency_factor` | нет | коэффициент эффективности |
| `stage_uid` | нет | этап для группировки |
| `is_active` | да | soft-disable связи |

Ключ уникальности: `order_uid + operation_uid + resource_uid`. Повторная передача обновляет связь, а не создаёт дубль.

Правила:

- `primary` — ровно один на производственную операцию для CCM;
- `alternative` — не занимает ресурс одновременно с primary; используется как вариант замены;
- `helper` — может быть несколько, занимает ресурс вместе с primary;
- несколько `primary` — ошибка `RESOURCE_PRIMARY_MULTIPLE`;
- нет `primary` — ошибка `RESOURCE_PRIMARY_MISSING` для CCM;
- `capacity_demand <= 0` — ошибка `RESOURCE_CAPACITY_INVALID`;
- альтернативный ресурс не должен попадать в фактическую загрузку, пока не выбран как основной.

### 4.5. Сотрудники, бригады и ресурсные профили

Справочники:

- `employee` — сотрудник: `uid`, `name`, `code`, `position`, `department_uid`, `is_active`, `version`;
- `department` — подразделение/бригада: `uid`, `name`, `parent_uid`, `level_code`, `kind`, `is_active`, `version`;
- бригада — это `org_unit`/`department` с настраиваемым уровнем `brigade`, а не оборудование;
- если в 1С есть отдельный справочник бригад, его можно передавать как `department` с `kind=brigade` или отдельным `brigade`-типом после согласования.

Ресурсный профиль:

- создаётся не для каждого сотрудника, а когда человек/бригада реально участвует в планировании;
- `Resource.resource_type = employee | team`;
- `Resource.subject_type = employee | org_unit`;
- `Resource.subject_uid` — UID сотрудника/подразделения;
- `Resource.capacity_mode = individual | pool`;
- `Resource.is_bookable = true` только для планируемых ресурсов.

При импорте связи `operation_uid + resource_uid` ProfyPlan должен найти ресурс по UID; если его нет — создать профиль из сотрудника/бригады или вернуть `RESOURCE_NOT_FOUND`, но не подменять оборудованием.

## 5. Что ProfyPlan делает с этими данными

1. Принимает `refs` сотрудников, подразделений, номенклатуры, ресурсов.
2. Принимает `orders` типов `production_order` и `work_order`.
3. Сопоставляет `operation_uid` и `resource_uid` по стабильным UID.
4. Создаёт/обновляет `OperationResource` с ролью и capacity.
5. Проверяет покрытие: у каждой производственной операции есть primary; альтернативы/помощники не ломают правило.
6. Строит CPM по операциям и зависимостям; ресурсы влияют на календарь и доступность.
7. Для CCM выполняет ресурсное выравнивание с учётом primary/helper и capacity.
8. Показывает пользователю список операций без primary и даёт назначить/исправить ресурс.
9. Формирует `plan_snapshot` только после успешной проверки; в 1С возвращает план, а не бухгалтерские документы.

## 6. Что должно приходить из 1С

### 6.1. Обязательный минимум для CCM

| Сущность | Что передать | Зачем |
|---|---|---|
| `refs.department` | подразделения и бригады, уровни | оргструктура и ресурсы |
| `refs.employee` | сотрудники, подразделение, активность | люди как ресурсы |
| `refs.nomenclature` | работы с `ntype=service` и `work_type` | строки заказ-наряда |
| `orders` | `production_order` и `work_order` | планируемые заказы |
| операции | `operation_uid`, `sequence`, `duration_hours` | CPM |
| связи | `operation_uid + resource_uid + role + capacity_demand` | CCM/M:N |
| календари | календарь ресурса/подразделения | доступность |
| версии | версия и `updated_at` | идемпотентность |

## 7. Ошибки и коды

| Код | Когда |
|---|---|
| `ORDER_TYPE_UNSUPPORTED` | тип заказа ещё не включён в MVP |
| `WORK_ORDER_METADATA_MISMATCH` | не подтверждено, какой объект 1С является заказ-нарядом |
| `WORK_TYPE_MISSING` | нет вида работы у строки работы |
| `OPERATION_UID_MISSING` | нет стабильного UID операции |
| `RESOURCE_NOT_FOUND` | ресурс не найден в ProfyPlan |
| `RESOURCE_TYPE_INVALID` | человек/бригада пришли как оборудование |
| `RESOURCE_PRIMARY_MISSING` | у производственной операции нет primary |
| `RESOURCE_PRIMARY_MULTIPLE` | больше одного primary |
| `RESOURCE_DUPLICATE` | повторная связь operation+resource |
| `RESOURCE_CAPACITY_INVALID` | capacity_demand <= 0 |
| `RESOURCE_ALTERNATIVE_CONFLICT` | альтернатива пытается грузиться одновременно |
| `EXECUTOR_TYPE_INVALID` | не employee/org_unit |
| `DEPENDENCY_CONFLICT` | удаление при активных зависимостях |

Ошибки по возможности возвращать в квитанции с `details.entity_uid` и `details.operation_uid`, чтобы 1С показывала конкретную строку.

## 8. Регистр в 1С

Если в 1С нет прямой связи «ресурс → операция», рекомендуется регистр сведений:

```text
ПФП_ОперацияРесурс

Измерения:
  Заказ          — ДокументСсылка (ЗаказНаПроизводство / ЗаказПокупателя)
  ТипЗаказа      — production_order / work_order
  ОперацияUID    — Строка(36)
  Ресурс         — СправочникСсылка

Ресурсы:
  Роль              — primary / alternative / helper
  КоличествоРесурса — Число(15,3)
  Длительность      — Число(10,3), необязательно
  Этап              — необязательно
  ИсточникСтроки    — необязательно
```

Требования:

- `ОперацияUID` стабилен и не зависит от номера строки;
- запись уникальна по `Заказ + ОперацияUID + Ресурс`;
- при удалении/перезаписи заказа связи помечаются неактивными, а не теряются молча;
- для людей/бригад `Ресурс` ссылается на сотрудника/подразделение, а не на оборудование;
- интерфейс связывания должен позволять выбрать операцию и ресурс, роль и количество, а также массово назначить ресурс на группу операций.

## 9. Возврат плана в 1С

`РесурсыПредприятия` в 1С — таблица уровня заказа, а не операции. Поэтому:

- ProfyPlan использует M:N внутри CCM;
- в `plan_snapshot` для 1С на первом этапе передаётся **primary-ресурс операции**; helper/alternative остаются в ProfyPlan;
- если 1С должна видеть все ресурсы операции, нужно расширить `plan_snapshot` полем `operation_uid` и поддержать несколько ресурсных строк на операцию;
- для заказ-наряда отдельно подтвердить, есть ли в 1С таблица, куда возвращать план; если нет — возвращать только факты/подтверждение, а план хранить в ProfyPlan.

## 10. Что нужно уточнить у 1С AI

1. Точное имя объекта заказ-наряда: `ЗаказПокупателя` + `ВидОперации=ЗаказНаряд` или отдельный `Документ.ЗаказНаряд`.
2. Где физически хранятся операции заказ-наряда и есть ли у строк стабильный UID.
3. Есть ли справочник видов работ или это реквизит номенклатуры.
4. Как заданы исполнители: отдельная ТЧ, `Ресурсы`, сотрудники в строках, бригады.
5. Бригада — справочник или подразделение; как определяется её состав.
6. Есть ли календарь/мощность у человека и бригады.
7. Должен ли заказ-наряд участвовать в CCM или только поставлять факты.
8. Куда 1С принимает план по заказ-наряду.
9. Можно ли добавить в расширение регистр `ПФП_ОперацияРесурс` и поле `ПФП_UIDОперации`.
10. Какие роли ресурсов реально используются: primary/alternative/helper или только основной.

## 11. Критерии приёмки

- заказ-наряд импортируется как `work_order` и не отбрасывается;
- номенклатура работы имеет `ntype=service` и вид работы;
- сотрудник/бригада создаются как `employee/team`, не `equipment`;
- связь operation+resource уникальна;
- у производственной операции ровно один primary для CCM;
- alternative не грузится одновременно с primary;
- helper учитывается в загрузке;
- ресурс может участвовать в нескольких операциях, операция — в нескольких ресурсах;
- отчёт готовности показывает конкретные операции без primary и позволяет их исправить;
- CCM-расчёт не выполняется при отсутствии primary (или требует явного подтверждения);
- plan_snapshot не теряет primary и явно сообщает об ограничении по helper/alternative;
- квитанция содержит UID операции и ресурса при ошибке.
