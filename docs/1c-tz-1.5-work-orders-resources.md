# ТЗ 1.5 для 1С AI: заказ-наряды, CCM/M:N и связи «операция ↔ ресурс»

**Дата:** 26.10.2026  
**Адресат:** разработчик расширения 1С  
**Основание:** ТЗ 1.4, решения ProfyPlan от 25–26.10.2026  
**Статус:** дополнение к `1c-tz-1.4.md`; обратная совместимость с `profyplan.exchange.v1` сохраняется

## 1. Зачем это дополнение

Пилот запускается вместе с CCM. Для CCM недостаточно передать заказ, номенклатуру и «Ресурсы предприятия» на уровне заказа: ProfyPlan должен понимать, **какая операция выполняется каким ресурсом**, сколько ресурса она занимает и какие ресурсы являются основными, альтернативными или вспомогательными.

Одновременно в обмен добавляется **заказ-наряд** — документ, где номенклатура имеет вид работы, а исполнителями являются люди и бригады. Текущий `orders` принимает только `production_order`, поэтому заказ-наряд сейчас отбрасывается.

Цель дополнения:

- принимать заказ-наряды как отдельный тип планируемого заказа;
- принимать людей и бригады как ресурсы, а не как оборудование;
- получать явную M:N-связь «операция ↔ ресурс»;
- обеспечивать корректный CCM: один основной ресурс на производственную операцию, альтернативы и помощники — по правилам;
- давать пользователю понятную проверку покрытия операций ресурсами и удобное исправление.

## 2. Главные решения

1. **1С остаётся ведущей системой** для справочников, заказов, операций, ресурсов и фактов.
2. **Спецификации как справочник ProfyPlan не используются.** Операции, ресурсы, подразделения и длительности берутся из заказа на производство или заказ-наряда.
3. **Заказ-наряд — отдельный тип `work_order`.** В модели 1С это `Документ.ЗаказПокупателя` с `ВидОперации = ВидыОперацийЗаказПокупателя.ЗаказНаряд` (форма `ФормаЗаказНаряда`), если в конкретной конфигурации нет отдельного документа. Точное имя объекта подтвердить по метаданным.
4. **В заказ-наряде строка работы сама является операцией планирования.** Отдельной ТЧ «Операции» нет; `line_uid` становится `operation_uid`, а исполнитель строки — primary-ресурсом.
5. **Связь «операция ↔ ресурс» — many-to-many.** Одна операция может использовать несколько ресурсов; один ресурс может участвовать в нескольких операциях.
6. **Для CCM у каждой производственной операции должен быть ровно один `primary`-ресурс.** Альтернативные ресурсы — варианты замены, а не одновременная загрузка. Вспомогательные ресурсы (`helper`) могут добавляться к основной операции.
7. **Структурная единица и этап не являются ключом связи.** Связь задаётся явно через `operation_uid + resource_uid`; эвристика по подразделению/этапу допустима только как подсказка, но не как единственный ключ.
8. **Сотрудники и бригады — не оборудование.** Для них используются `employee`/`org_unit` и ресурсные профили `employee`/`team`.
9. **Без явной связи CCM не считается корректным.** CPM может работать без ресурсов; CCM — нет.

## 3. Термины

| Термин | Смысл |
|---|---|
| `production_order` | Заказ на производство |
| `work_order` | Заказ-наряд: работы, люди, бригады |
| `operation_uid` | Стабильный UID строки операции |
| `resource_uid` | UID ресурса: человек, бригада, оборудование, рабочее место |
| `primary` | Основной ресурс операции; определяет длительность/загрузку |
| `member` | Дополнительный исполнитель работы; учитывается в КТУ, но не создаёт второй primary |
| `alternative` | Возможная замена; не занимает ресурс одновременно с primary |
| `helper` | Вспомогательный ресурс, занятый вместе с primary |
| `capacity_demand` | Сколько единиц ресурса требует операция |
| `ktu` | Коэффициент трудового участия исполнителя; влияет на распределение, не на CCM |
| `resource_type` | `employee`, `team`, `equipment`, `workplace` |

## 4. Целевая модель заказ-наряда

### 4.1. Шапка `work_order`

| Поле | Обязательность | Комментарий |
|---|---|---|
| `uid` | да | UID документа 1С |
| `order_type` | да | строго `work_order` |
| `number` | да | номер документа |
| `date` | да | дата документа |
| `organization_uid` | да | организация |
| `customer_uid` | да | заказчик, если есть |
| `project_uid` | нет | проект ProfyPlan, если уже связан |
| `parent_production_order_uid` | нет | родительский заказ на производство, если заказ-наряд выпущен по нему |
| `status` | да | статус документа 1С |
| `comment` | нет | комментарий |
| `version` | да | версия из регистра версий |
| `updated_at` | да | время версии |

### 4.2. Строки работ

| Поле | Обязательность | Комментарий |
|---|---|---|
| `line_uid` | да | стабильный UID строки |
| `nomenclature_uid` | да | номенклатура |
| `nomenclature_kind` | да | `service` (Услуга) или `work` (Работа); это вид номенклатуры, не операция |
| `work_type_uid` | желательно | вид работы, если есть отдельный справочник |
| `work_type_name` | да, если нет UID | человекочитаемый вид работы |
| `quantity` | да | количество |
| `unit_uid` | да | единица измерения |
| `department_uid` | нет | подразделение выполнения |
| `stage_uid` | нет | этап |
| `sequence` | нет | порядок строки в заказе/этапе |
| `duration_hours` | да для планирования | нормативная длительность работы, десятичные часы |
| `setup_hours` | нет | подготовительно-заключительное время |
| `executor_uid` | да для CCM | исполнитель: сотрудник или бригада |
| `executor_type` | да для CCM | `employee` или `org_unit` |
| `executors` | да, если исполнителей несколько | массив исполнителей с ролью и КТУ |
| `price` | нет | цена, если нужна для отчётности |

Номенклатура заказ-наряда может иметь вид **«Услуга»** или **«Работа»**. Это вид номенклатуры, а не отдельная операция. Но **строка работы в заказ-наряде сама является планировочной операцией**: отдельных строк `operations` в заказ-наряде нет, и их не нужно искусственно создавать.

Внутри ProfyPlan допускается `ntype = "service"` для обеих видов, но точный вид 1С нужно сохранять в `nomenclature_kind` (`service` / `work`), чтобы не потерять различие. Если 1C уже отдаёт `ntype` со значениями `service`/`work`, это также допустимо. Конкретный вид работ (`work_type_uid/name`) — отдельное, необязательное уточнение.

### 4.3. Строка работы как операция планирования

В заказ-наряде нет отдельной ТЧ «Операции». Для ProfyPlan каждая строка работы становится операцией:

- `operation_uid = line_uid` (или стабильный `ПФП_UIDСтроки`);
- `operation_name = work_type_name` или имя номенклатуры;
- `duration_hours` берётся из строки работы;
- `executor_uid/executor_type` становятся **primary-ресурсом** операции;
- `department_uid` и `stage_uid` переносятся в операцию.

Если вкладка исполнителей допускает несколько сотрудников/бригад на одну строку, нужно передавать `executors[]` с ролью `primary` / `member` / `helper` / `alternative`; один из них обязан быть primary. Если вкладка допускает только одного исполнителя, достаточно `executor_uid/executor_type`.

КТУ (`ktu`) — коэффициент трудового участия. Он хранится у каждого исполнителя строки и используется для распределения трудозатрат/оплаты, но **не влияет на длительность операции и не меняет ресурсное выравнивание CCM**. Нельзя делать несколько primary только потому, что у нескольких исполнителей есть КТУ: для CCM primary должен быть один — сотрудник или бригада.

В 1С у строки работы нет стабильного UID. Для MVP используем детерминированный ключ:

```text
line_uid = <UID документа> + ":" + <КлючСвязи>
```

`КлючСвязи` в заказ-наряде — Число(5), уникальное внутри документа. Этого достаточно, чтобы не делать ручное заимствование ТЧ в расширение. Если позже понадобится устойчивость к удалению/пересозданию строки, добавляем `ПФП_UIDСтроки` в ТЧ «Работы» и переходим на него. `НомерСтроки` как ключ не используем.

Для операции заказа на производство используем `ПФП_UIDОперации` или аналогичный детерминированный ключ `<UID заказа>:<ключ строки>`.

Без `duration_hours` и исполнителя CCM по строке не рассчитывается.

### 4.4. Связь операции с ресурсом

| Поле | Обязательность | Комментарий |
|---|---|---|
| `order_uid` | да | заказ, к которому относится связь |
| `order_type` | да | `production_order` или `work_order` |
| `operation_uid` | да | операция |
| `resource_uid` | да | ресурс |
| `resource_type` | да | `employee`, `team`, `equipment`, `workplace` |
| `role` | да | `primary`, `alternative`, `helper` |
| `capacity_demand` | да | количество единиц ресурса, обычно `1` |
| `duration_override_hours` | нет | переопределение длительности |
| `efficiency_factor` | нет | коэффициент эффективности |
| `ktu` | нет | коэффициент трудового участия исполнителя; не влияет на CCM-длительность |
| `stage_uid` | нет | этап для группировки |
| `is_active` | да | soft-disable связи |

Ключ уникальности: `order_uid + operation_uid + resource_uid`. Повторная передача обновляет связь, а не создаёт дубль.

Для заказ-наряда `operation_uid` — это `line_uid` строки работы. Если исполнитель уже указан в строке (`executor_uid/executor_type`), ProfyPlan создаёт связь `primary` автоматически; `executors[]` нужен только для нескольких исполнителей или ролей.

Если на строку назначены несколько сотрудников одной бригады, правильная модель — **бригада как primary `team`-ресурс**, а сотрудники — `member` с КТУ. Если бригады как ресурса нет, выбирается один primary-сотрудник, остальные становятся `member`/`helper`; количество primary всё равно остаётся один.

Правила:

- `primary` — ровно один на производственную операцию для CCM;
- `alternative` — не занимает ресурс одновременно с primary; используется как вариант замены;
- `helper` — может быть несколько, занимает ресурс вместе с primary;
- несколько `primary` — ошибка `RESOURCE_PRIMARY_MULTIPLE`;
- нет `primary` — ошибка `RESOURCE_PRIMARY_MISSING` для CCM;
- `capacity_demand <= 0` — ошибка `RESOURCE_CAPACITY_INVALID`;
- альтернативный ресурс не должен попадать в фактическую загрузку, пока не выбран как основной.

Для MVP в 1С не нужно вводить роли `alternative` и `helper` вручную. Автоматически заполняются:

- `primary` — ресурс из закладки «Ресурсы», если он задан; иначе первый исполнитель строки;
- `member` — остальные исполнители строки с КТУ.

`alternative` и `helper` остаются в модели ProfyPlan как задел и вводятся только в расширенном режиме ProfyPlan, если это понадобится после пилота.

### 4.5. Сотрудники, бригады и ресурсные профили

Справочники:

- `employee` — сотрудник: `uid`, `name`, `code`, `position`, `department_uid`, `is_active`, `version`;
- `department` — подразделение/бригада: `uid`, `name`, `parent_uid`, `level_code`, `kind`, `is_active`, `version`;
- бригада — это `org_unit`/`department` с настраиваемым уровнем `brigade`, а не оборудование;
- если в 1С есть отдельный справочник бригад, его можно передавать как `department` с `kind=brigade` или отдельным `brigade`-типом после согласования.

Ресурсный профиль:

- создаётся не для каждого сотрудника, а когда человек/бригада реально участвует в планировании;
- `Resource.resource_type = employee | team`;
- `Resource.subject_type = employee | org_unit`;
- `Resource.subject_uid` — UID сотрудника/подразделения;
- `Resource.capacity_mode = individual | pool`;
- `Resource.is_bookable = true` только для планируемых ресурсов.

При импорте связи `operation_uid + resource_uid` ProfyPlan должен найти ресурс по UID; если его нет — создать профиль из сотрудника/бригады или вернуть `RESOURCE_NOT_FOUND`, но не подменять оборудованием.

## 5. Что ProfyPlan делает с этими данными

1. Принимает `refs` сотрудников, подразделений, номенклатуры, ресурсов.
2. Принимает `orders` типов `production_order` и `work_order`.
3. Сопоставляет `operation_uid` и `resource_uid` по стабильным UID.
4. Создаёт/обновляет `OperationResource` с ролью и capacity.
5. Проверяет покрытие: у каждой производственной операции есть primary; альтернативы/помощники не ломают правило.
6. Строит CPM по операциям и зависимостям; ресурсы влияют на календарь и доступность.
7. Для CCM выполняет ресурсное выравнивание с учётом primary/helper и capacity.
8. Показывает пользователю список операций без primary и даёт назначить/исправить ресурс.
9. Формирует `plan_snapshot` только после успешной проверки; в 1С возвращает план, а не бухгалтерские документы.

## 6. Что должно приходить из 1С

### 6.1. Обязательный минимум для CCM

## 7. Ошибки и коды

| Код | Когда |
|---|---|
| `ORDER_TYPE_UNSUPPORTED` | тип заказа ещё не включён в MVP |
| `WORK_ORDER_METADATA_MISMATCH` | не подтверждено, какой объект 1С является заказ-нарядом |
| `WORK_TYPE_MISSING` | нет вида работы у строки работы |
| `OPERATION_UID_MISSING` | нет стабильного UID операции |
| `RESOURCE_NOT_FOUND` | ресурс не найден в ProfyPlan |
| `RESOURCE_TYPE_INVALID` | человек/бригада пришли как оборудование |
| `RESOURCE_PRIMARY_MISSING` | у производственной операции нет primary |
| `RESOURCE_PRIMARY_MULTIPLE` | больше одного primary |
| `RESOURCE_DUPLICATE` | повторная связь operation+resource |
| `RESOURCE_CAPACITY_INVALID` | capacity_demand <= 0 |
| `KTU_INVALID` | КТУ не число или вне согласованного диапазона |
| `RESOURCE_ALTERNATIVE_CONFLICT` | альтернатива пытается грузиться одновременно |
| `EXECUTOR_TYPE_INVALID` | не employee/org_unit |
| `NOMENCLATURE_KIND_INVALID` | вид номенклатуры не service/work |
| `DEPENDENCY_CONFLICT` | удаление при активных зависимостях |

Ошибки по возможности возвращать в квитанции с `details.entity_uid` и `details.operation_uid`, чтобы 1С показывала конкретную строку.

## 8. Регистр в 1С

**`ПФП_РесурсыОпераций` — это регистр сведений в расширении конфигурации 1С УНФ**, а не таблица ProfyPlan. Внутри ProfyPlan связи хранятся в `operation_resources` (`OperationResource`); это разные уровни.

Если префикс не нужен, допустимо имя `РесурсыОпераций`, но `ПФП_` лучше сохраняет совместимость с `ПФП_ВерсииОбъектов` и не конфликтует с типовыми объектами.

Для **заказ-наряда отдельный регистр не обязателен**: связь строки работы с исполнителем уже хранится в документе. Регистр нужен прежде всего для заказа на производство, где `РесурсыПредприятия` не связаны с операциями. Если удобнее вести обе связи в одном месте, регистр может принимать и строки заказ-наряда (`ОперацияUID = line_uid`), но это не обязательно.

Если в 1С нет прямой связи «ресурс → операция», рекомендуется регистр сведений:

```text
ПФП_РесурсыОпераций

Измерения:
  Заказ          — ДокументСсылка (ЗаказНаПроизводство / ЗаказПокупателя)
  ТипЗаказа      — production_order / work_order
  ОперацияUID    — Строка(36)
  Ресурс         — СправочникСсылка

Ресурсы:
  Роль              — primary / member / alternative / helper
  КоличествоРесурса — Число(15,3)
  Длительность      — Число(10,3), необязательно
  КТУ               — Число(8,3), необязательно
  ПланСтарт         — Дата+Время, только для primary
  ПланФиниш         — Дата+Время, только для primary
  Версия            — Число
  Этап              — необязательно
  ИсточникСтроки    — необязательно
```

Требования:

- `ОперацияUID` стабилен и не зависит от номера строки;
- запись уникальна по `Заказ + ОперацияUID + Ресурс`;
- план операции (`ПланСтарт`, `ПланФиниш`, `Длительность`) хранится в строке `primary`; у `member`/`helper` эти поля не дублируются;
- при удалении/перезаписи заказа связи помечаются неактивными, а не теряются молча;
- для людей/бригад `Ресурс` ссылается на сотрудника/подразделение, а не на оборудование;
- интерфейс связывания должен позволять выбрать операцию и ресурс, роль и количество, а также массово назначить ресурс на группу операций.

### 8.1. Передача регистра в ProfyPlan

Если регистр выгружается отдельными сущностями, использовать тип `operation_resource` в `entities`:

```json
{
  "type": "operation_resource",
  "uid": "ORDER-UID:OPERATION-UID:RESOURCE-UID",
  "op": "upsert",
  "fields": {
    "order_uid": "ORDER-UID",
    "order_type": "work_order",
    "operation_uid": "OPERATION-UID",
    "resource_uid": "RESOURCE-UID",
    "role": "primary",
    "capacity_demand": 1,
    "ktu": 1.0,
    "plan_start": "2026-10-27T09:00:00+03:00",
    "plan_finish": "2026-10-27T13:30:00+03:00"
  }
}
```

ProfyPlan сопоставляет `order_uid + operation_uid` с операцией, `resource_uid` — с ресурсом, и сохраняет связь в `OperationResource`; `plan_start/plan_finish` используются для плана по операции. Повторная передача обновляет строку, а не создаёт дубль.

## 9. Возврат плана в 1С

`РесурсыПредприятия` в 1С — таблица уровня заказа, а не операции. Поэтому:

- ProfyPlan использует M:N внутри CCM;
- `plan_snapshot` возвращает план **по операциям**: одна или несколько строк на `operation_uid` с `resource_uid`, `role`, `start`, `finish`, `duration_hours`, `ktu`;
- `primary`-строка операции содержит плановые старт/финиш/длительность; `member`/`helper` — связь и КТУ без дублирования дат;
- 1С обновляет `РесурсыПредприятия` по primary-строкам, а полный план операций пишет в `ПФП_РесурсыОпераций`;
- для этого `plan_snapshot` расширяется полем `operation_uid` и поддерживает несколько ресурсных строк на операцию.

## 10. Что нужно уточнить у 1С AI

Ответы 1С AI и принятые решения по этим вопросам — в §12. Ниже оставлены исходные формулировки для трассировки.

1. Точное имя объекта заказ-наряда: `ЗаказПокупателя` + `ВидОперации=ЗаказНаряд` или отдельный `Документ.ЗаказНаряд`.
2. Подтвердить, что строка работы заказ-наряда является операцией планирования; есть ли отдельная ТЧ операций и стабильный UID строки.
3. Есть ли справочник видов работ или это реквизит номенклатуры.
4. Как заданы исполнители: один сотрудник/бригада на строку или несколько через вкладку; можно ли указать роль.
5. Бригада — справочник или подразделение; как определяется её состав.
6. Есть ли календарь/мощность у человека и бригады.
7. Должен ли заказ-наряд участвовать в CCM или только поставлять факты.
8. Куда 1С принимает план по заказ-наряду.
9. Можно ли добавить в расширение регистр `ПФП_РесурсыОпераций` и поле `ПФП_UIDОперации`.
10. Какие роли ресурсов реально используются: primary/alternative/helper или только основной.
11. Какие точные значения `ВидНоменклатуры` используются для «Услуга» и «Работа» и есть ли отдельный вид работы.
12. Подтвердить, что строки работ являются операциями планирования и не требуют отдельной ТЧ «Операции».
13. В каком виде хранится КТУ: коэффициент (`1.0`) или проценты (`100`), какой диапазон и как распределяется между исполнителями.
14. Может ли одна строка иметь несколько бригад/сотрудников одновременно; кто считается primary.

## 11. Критерии приёмки

- заказ-наряд импортируется как `work_order` и не отбрасывается;
- строка работы становится операцией (`operation_uid = line_uid`), отдельный массив `operations` не требуется;
- номенклатура работы имеет `nomenclature_kind=service / work` и при необходимости `work_type`;
- вид номенклатуры «Услуга/Работа» не подменяет операцию и не теряет различие;
- сотрудник/бригада создаются как `employee/team`, не `equipment`;
- связь operation+resource уникальна;
- у производственной операции ровно один primary для CCM;
- alternative не грузится одновременно с primary;
- helper учитывается в загрузке;
- несколько исполнителей с КТУ сохраняются как `member`; primary остаётся один;
- КТУ не меняет duration/CCM, но сохраняется для распределения трудозатрат;
- ресурс может участвовать в нескольких операциях, операция — в нескольких ресурсах;
- отчёт готовности показывает конкретные операции без primary и позволяет их исправить;
- CCM-расчёт не выполняется при отсутствии primary (или требует явного подтверждения);
- plan_snapshot не теряет primary и явно сообщает об ограничении по helper/alternative;
- квитанция содержит UID операции и ресурса при ошибке.

## 12. Ответы 1С AI и принятые решения (26.10.2026)

### 12.1. Заказ-наряд

Подтверждено: отдельного `Документ.ЗаказНаряд` нет. Используется `Документ.ЗаказПокупателя` с `ВидОперации = ЗаказНаряд`. В документе есть закладка «Ресурсы» с планируемым исполнителем и временем; в шапке — плановые Старт/Финиш. Планирование ресурсов опционально и включается настройкой «Планирование работ в документе Заказ-наряд».

### 12.2. UID строки

Для MVP используем детерминированный ключ:

```text
line_uid = <UID документа> + ":" + <КлючСвязи>
```

`КлючСвязи` — Число(5), уникальное внутри документа. Ручное заимствование ТЧ «Работы» в расширение не требуется. `ПФП_UIDСтроки` добавляем только если понадобится устойчивость к удалению/пересозданию строки.

### 12.3. Primary: ресурс или исполнитель

Приоритет:

1. Если в строке заполнен ресурс из закладки «Ресурсы» — он `primary` (оборудование/рабочее место/бригада).
2. Если ресурса нет — первый исполнитель по порядку строки становится `primary`.
3. Остальные исполнители — `member` с КТУ.

Это правильно для CCM: ограничение по оборудованию/рабочему месту важнее, чем отдельный сотрудник. Если ресурс не является планируемой ёмкостью (`is_bookable=false`), он не должен становиться primary; в таком случае primary — первый исполнитель.

### 12.4. Роли

В 1С ролей нет. Для MVP:

- `primary` и `member` заполняются автоматически по правилу выше;
- `alternative` и `helper` не требуют ввода в 1С и остаются заделом ProfyPlan;
- ручной ввод alternative/helper в регистр 1С не нужен для пилота.

### 12.5. Регистр

Принята структура регистра расширения 1С **`ПФП_РесурсыОпераций`** (не путать с `operation_resources` в ProfyPlan):

- измерения: `Заказ`, `ТипЗаказа`, `ОперацияUID`, `Ресурс`;
- ресурсы: `Роль`, `КоличествоРесурса`, `КТУ`, `Длительность`, `ПланСтарт`, `ПланФиниш`, `Версия`, `ИсточникСтроки`;
- уникальность: `Заказ + ОперацияUID + Ресурс`;
- план операции хранится в строке `primary`, у `member`/`helper` даты не дублируются;
- регистр обязателен для обоих типов заказов; для заказ-наряда `ОперацияUID = line_uid`.

### 12.6. `plan_snapshot`

Возвращаем план **по операциям**, а не агрегат по документу. В `plan_snapshot` добавляются:

- `operation_uid`;
- `resource_uid`;
- `role`;
- `start`, `finish`, `duration_hours`;
- `ktu`.

На одну операцию допускается несколько ресурсных строк. 1С обновляет `РесурсыПредприятия` по primary-строке, а полный план пишет в `ПФП_РесурсыОпераций`.

### 12.7. Факты

Для MVP:

- закрытие заказ-наряда — факт статуса/завершения;
- `СдельныйНаряд` — источник фактических часов и исполнителей;
- отдельный факт по каждой строке работы нужен, если в `СдельныйНаряд` есть фактические часы по строке/исполнителю; иначе достаточно закрытия документа;
- нельзя одновременно считать один и тот же объём из `СдельныйНаряд` и закрытия — нужен один источник истины и идемпотентный UID.

### 12.8. КТУ

КТУ — коэффициент (`1.0`, `0.8`), не проценты. Диапазон MVP: `0.1–3.0`, по умолчанию `1.0`. Распределение пропорционально КТУ. КТУ влияет на трудозатраты/оплату, но **не меняет длительность операции и CCM-выравнивание**. В фактах КТУ передаётся вместе с фактическими часами, если он используется для распределения оплаты; иначе хранится только в плане.

### 12.9. `bom` и `routes`

Оставляем как страховку. Отключаем флагом только после успешного тестового заказа, в котором операции, ресурсы, исполнители и КТУ уже приходят внутри `orders`.
