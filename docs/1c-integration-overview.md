# Интеграция ProfyPlan с 1С: как задумано и что реализовано

**Статус:** рабочая локальная реализация, файловый обмен и облачные каналы; production не обновлялся.

## 1. Главная идея

Интеграция двухконтурная:

1. **1С → ProfyPlan**: справочники и заказы на производство — это входные данные для планирования.
2. **ProfyPlan → 1С**: только зафиксированный план производства в виде `plan_snapshot`; 1С записывает ресурсы, старт и финиш в заказ.

Это не двусторонняя синхронизация всех сущностей. 1С остаётся мастером справочников и заказов, ProfyPlan — мастером операций, маршрутов, ресурсного планирования и расчётов.

## 2. Транспорты

| Транспорт | Как работает | Состояние |
|---|---|---|
| Файловый каталог | 1С пишет `refs`/`orders`/`ping` в `in`, ProfyPlan читает; план — в `out` | Основной рабочий сценарий |
| Помощник обмена (Chromium) | Расширение читает локальную папку и загружает пакеты через API | MVP |
| Companion Windows | Трей-агент следит за локальной папкой, забирает outbox | MVP, без подписи |
| Яндекс Диск | Канонические папки в облаке, OAuth, polling | Первый срез + UI и планировщик |
| Google Drive | То же, OAuth + `drive`, ID папок | Первый срез + UI и планировщик |
| OData | ProfyPlan читает справочники 1С напрямую | Тест и загрузка справочников |
| Прямой HTTP | Обмен с HTTP-сервисом 1С | В UI есть поля, рабочего обмена нет |

Для облака ProfyPlan умеет: найти корневую папку по имени или создать её, создать канонические папки, проверить доступ, принять входящие, выгрузить исходящие, обновить OAuth-токен и опросить по расписанию.

## 3. Входящий поток: 1С → ProfyPlan

Последовательность:

1. 1С формирует пакет `profyplan.exchange.v1`:
   - `ping` — проверка канала;
   - `refs` — номенклатура, контрагенты, подразделения, ресурсы, проекты;
   - `orders` — заказы на производство.
2. Пакет попадает в `1c_to_plan` (облако) или `in` (файловый канал).
3. ProfyPlan вызывает «Скан каталога» или облачный `poll`:
   - проверяет `schema`;
   - создаёт запись журнала;
   - для `ping` сразу фиксирует успех;
   - для `refs`/`orders` создаёт элементы очереди `ExchangeInboxItem` со статусом `pending`;
   - переносит файл в `processed` (облако) или `processed` (каталог).
4. Пользователь нажимает «Применить очередь».
5. `apply_pending` разбирает элементы:
   - `nomenclature` — создаёт/обновляет номенклатуру;
   - `counterparty` — контрагента;
   - `department` — подразделение;
   - `resource` — ресурс;
   - `project` — **только сопоставляет** существующий проект, новый не создаёт;
   - `order` — создаёт черновик заказа или обновляет существующий черновик.
6. Каждый элемент получает `applied` / `skipped` / `error`, всё пишется в журнал обмена.

### Ключи сопоставления

В сущностях ProfyPlan хранятся:

- `ext_uid` — GUID объекта 1С, главный ключ;
- `ext_id` / `external_code` — номер или код, резервный ключ;
- имя — последний резерв для некоторых сущностей.

Порядок: `ext_uid → ext_id/external_code/code → имя`.

Исправлено в текущей итерации:

- заказ ищется сначала по `ext_uid`, затем по номеру;
- ресурс принимает `external_code`;
- проект принимает `code`.

### Что создаётся, а что только сопоставляется

- Номенклатура, контрагент, подразделение, ресурс — могут создаваться.
- Проект — только сопоставляется; если в 1С есть проект, которого нет в ProfyPlan, элемент будет `skipped`.
- Заказ — создаётся черновиком.
- Операции, маршруты и состав изделия из 1С не импортируются: это локальные данные ProfyPlan.

### Правила обновления заказа

Импортированный заказ обновляется из 1С, только если он:

- в статусе `draft`;
- ещё не развёрнут (`exploded_at is None`).

Согласованный или развёрнутый заказ не перезаписывается. Это защищает ручные операции и планировочные решения.

## 4. Исходящий поток: ProfyPlan → 1С

В 1С уходит не весь расчёт, а **снимок зафиксированного плана**:

1. Пользователь рассчитывает проект.
2. Нажимает «Зафиксировать план» — создаётся `PlanSnapshot`.
3. В интеграции выбирает проект и фиксацию, нажимает «Экспорт фиксации».
4. Формируется `plan_snapshot_<id>_<timestamp>.json` с массивом `plan_row`.
5. Файл попадает в `out` или `plan_to_1c` (облако).
6. 1С читает пакет и записывает строки в `РесурсыПредприятия` заказа:
   - заказ — по `order_ext_uid`, резерв — `order_ext_id`;
   - ресурс — по `resource_ext_uid`, резерв — `resource_ext_id`, затем имя;
   - старт/финиш;
   - загрузка ресурса (`resource_load`, в v1 = 1);
   - длительность вычисляет 1С.

1С не создаёт операции и не меняет проект заказа по плану. Она применяет ресурсные строки к уже существующему заказу. Если заказ не найден, строка пропускается.

## 5. Что происходит при локальных изменениях

| Действие в ProfyPlan | Сейчас |
|---|---|
| Добавить операцию в импортированный заказ | Операция остаётся локальной. В план уходят ресурс/время; 1С саму операцию не создаёт |
| Сменить проект у заказа | Меняется только `project_id` ProfyPlan; в план это не входит и в 1С не уходит |
| Переименовать проект | Локальное имя сохраняется; 1С имя не обновляет |
| Создать проект или подпроект | Локальная сущность, в 1С не выгружается |
| Создать заказ в ProfyPlan | В 1С не выгружается; у него нет `ext_uid`, поэтому план не сопоставится |
| Изменить справочник | Следующий `refs` из 1С перезапишет имя/поля (кроме проекта) |
| Изменить заказ после развёртывания | Импорт из 1С его уже не перезаписывает |

## 5.1. Типы документов 1С и текущая модель ProfyPlan

В ProfyPlan сейчас есть один тип заказа — **`ProductionOrder` («Заказ на производство»)**. Он может быть листовым или иметь `parent_order_id`, то есть поддерживает дерево заказов. Группы и пулы заказов — это планировочные объединения ProfyPlan, а не документы 1С.

| Документ 1С | Сейчас в ProfyPlan |
|---|---|
| Заказ на производство | `ProductionOrder` — импортируется и планируется |
| Заказ-наряд | Отдельной сущности нет |
| Заказ поставщику | Отдельной сущности нет; есть только календарь поставщика |
| Заказ на перемещение | Отдельной сущности нет |

Входящий пакет `orders` не содержит типа документа, поэтому все заказы из него создаются как `ProductionOrder`. Если в будущем 1С начнёт передавать заказ-наряд, заказ поставщику или перемещение в том же `orders`, их нельзя импортировать как производственные заказы — нужен отдельный `kind`/`order_type` и отдельные модели.

## 6. Где хранится трансляция

Отдельной таблицы «соответствий» нет. Связь хранится в самих сущностях:

- `Project.ext_uid`, `Project.ext_id`;
- `ProductionOrder.ext_uid`, `ProductionOrder.ext_id`;
- `Nomenclature`, `Counterparty`, `Department`, `Resource` — `ext_uid` / `ext_id` / `external_code`;
- `PlanSnapshotRow` — `order_ext_uid`, `order_ext_id`, `resource_ext_uid`, `resource_ext_id`, `department_ext_uid`.

Это простая и предсказуемая схема, но у неё нет истории переименований и явного владельца поля. Для production-сценария с несколькими источниками стоит добавить таблицу `external_links` с типом сущности, локальным ID, UID, кодом, системой-источником и политикой обновления.

## 7. Текущие ограничения

1. Нет обратной выгрузки локальных проектов, подпроектов и заказов в 1С.
2. Смена проекта у заказа не передаётся в 1С.
3. Новые операции не создаются в 1С; передаются только ресурсные строки плана.
4. `priority`/`project` в `orders` описаны в 1С противоречиво: раздел 6.4 говорит, что их нет, раздел «Сделано» — что добавлены. Нужен реальный пакет.
5. `process_incoming` принимает пакет без проверки уже обработанного `packet_id`; 1С ведёт такой регистр.
6. OData работает только на чтение справочников; прямое HTTP-подключение пока не реализовано.
7. Для облака нужен shared-доступ к корневой папке и реальный тест OAuth.

## 8. Что предлагаю зафиксировать как правило

- 1С — владелец справочников, заказов и корневой папки обмена.
- ProfyPlan — владелец операций, маршрутов, ресурсного планирования и зафиксированного плана.
- Локальные проекты/подпроекты/заказы не отправляются в 1С, пока не появится отдельный outbound-контракт.
- Смена проекта у импортированного заказа — локальное переопределение; если её нужно передавать, это отдельный пакет и доработка 1С.
- Перед изменением импортированного заказа пользователь видит, что заказ из 1С, и что часть полей может быть перезаписана.
- Для production добавить дедупликацию `packet_id`, журнал конфликтов и, при необходимости, таблицу `external_links`.

## 7. После пилота: документы «Событие: Запись», «Задание на работу», «Учёт времени»

**Статус:** отложено до завершения пилота и проверки ограниченного режима.

### «Событие: Запись»

Это **не** `ResourceEvent` (ремонт/простой/изменение мощности). Если по данным 1С это запись на услугу/приём, её нужно моделировать как **`ResourceBooking`**:

- ресурс/врач/кабинет/оборудование;
- услуга;
- клиент/пациент;
- `start`, `finish`;
- статус: план, подтверждена, выполнена, отменена;
- `ext_uid`, `source_document_uid`, `source_row_uid`;
- проект — если услуга относится к проекту.

Такая запись занимает ресурс на интервал, но не меняет его мощность. Включать её в расчёт можно только настройкой **«Учитывать записи на услуги в планировании»**; по умолчанию выключено. Если записи не связаны с производственными ресурсами, импортировать их не нужно.

### «Задание на работу»

Отдельная `WorkTask`, не `Operation`:

- проект;
- заказ на производство и/или операция;
- ресурс или исполнитель;
- плановые даты;
- плановые часы/количество;
- статус;
- `ext_uid`, `ext_id`, `source`.

Импортировать только если задание влияет на загрузку ресурса/исполнителя; иначе оставить за пределами планирования или включить отдельной настройкой.

### «Учёт времени»

Компактный факт `WorkTimeFact`:

- `work_task_id`;
- дата;
- фактические часы;
- исполнитель;
- `source_document_uid`, `source_row_uid`.

Факт обновляется по UID, не копирует бухгалтерский документ. Изменение факта ставит проекту индикатор «Есть новые факты — пересчитайте».

### Что не делать

- Не маппить «Событие: Запись» в `ResourceEvent`.
- Не копировать полные документы 1С.
- Не смешивать `WorkTask` с `Operation`.
- Не импортировать задачи, не влияющие на ресурсы, без настройки.
- Не передавать эти документы обратно в 1С в ограниченном режиме.

### Условия возврата к теме

- Пилот завершён и ограниченный режим стабилен.
- Подтверждены реальные поля документов 1С.
- Понятно, какие ресурсы пересекаются с производственным планированием.
- Есть владелец продукта для настройки «учитывать/не учитывать» записи и задания.
