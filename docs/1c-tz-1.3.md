# ТЗ 1.3 для 1С AI: обмен с ProfyPlan (ограниченный режим)

**Дата:** 24.10.2026  
**Статус:** к реализации после пилота; MVP — 1С ведущая система  
**Связанные документы:** `docs/1c-exchange-schema.md`, `docs/1c-sync-decisions.md`

## 1. Назначение и границы

1С остаётся ведущей системой для справочников, заказов, плановых документов, фактов и учётных реквизитов. ProfyPlan получает данные, планирует и возвращает только **зафиксированный план**.

В этом ТЗ **не требуется**:

- создавать бухгалтерские документы 1С из ProfyPlan;
- передавать в 1С операции, маршруты и этапы как учётные документы;
- копировать проводки, налоги, оплаты, остатки;
- делать полный двусторонний обмен документами.

Все новые пакеты должны быть обратно совместимы с `profyplan.exchange.v1`.

## 2. Общие требования к пакетам

| Поле | Требование |
|---|---|
| `schema` | `profyplan.exchange.v1` |
| `packet_id` | Уникальный ID пакета; повторный пакет не должен создавать дубли |
| `direction` | `in` для данных 1С → ProfyPlan |
| `kind` | Тип пакета |
| `generated_at` | ISO-8601 |
| `source.system` | Идентификатор системы 1С |
| `entities` | Массив сущностей |

Каждая сущность:

```json
{
  "type": "organization",
  "uid": "GUID 1С",
  "op": "upsert",
  "fields": {},
  "updated_at": "2026-10-24T12:00:00",
  "version": 12
}
```

Требования:

- `uid` — стабильный GUID объекта 1С; обязателен для всех импортируемых сущностей.
- `updated_at` и `version` — обязательны для конфликтов и ревизий; если 1С не может дать версию, передавать хотя бы `updated_at`.
- `op`: `upsert`, `delete` или `cancel` (для документов).
- Неизвестный `type`/`kind` не должен создавать сущность; пакет уходит в ошибки с понятным сообщением.

## 3. Канонические папки

Структура едина для Яндекс Диска и Google Drive:

```
<корень>/
  1c_to_plan/
  plan_to_1c/
  processed/
    1c_to_plan/
    plan_to_1c/
  archive/
    ГГГГ-ММ/
  _state/
```

Правила:

- `archive/ГГГГ-ММ` — месяц обработки в московской шкале.
- Существующие папки не переименовывать и не создавать дубли.
- Если корень создаёт 1С, он должен быть расшарен ProfyPlan с правом «Редактор»; для Google используется scope `drive`.

## 4. Справочники (`kind: refs`)

### 4.1 Организация

| Поле | Обязательное | Комментарий |
|---|---|---|
| `name` | да | краткое наименование |
| `full_name` | нет | полное наименование |
| `inn` | нет | ИНН |
| `kpp` | нет | КПП |
| `ogrn` | нет | ОГРН |
| `is_default` | нет | организация по умолчанию |
| `is_active` | да | активность |
| `uid` | да | GUID |

### 4.2 Склад

| Поле | Обязательное | Комментарий |
|---|---|---|
| `name` | да | наименование |
| `code` | нет | код |
| `organization_uid` | нет | если склад привязан к организации |
| `department_uid` | **нет** | группа/подразделение в 1С может отсутствовать |
| `is_active` | да | активность |
| `uid` | да | GUID |

`department_uid` не должен блокировать импорт. Если его нет, ProfyPlan создаёт склад с пустым подразделением и признаком «требует привязки».

### 4.3 Проект и дерево проектов

| Поле | Обязательное | Комментарий |
|---|---|---|
| `name` | да | имя |
| `code` | нет | код |
| `parent_uid` | нет | родительский проект |
| `organization_uid` | нет | если проект относится к организации |
| `is_active` | да | активность |
| `uid` | да | GUID |

1С передаёт дерево; ProfyPlan не создаёт проект, если его нет, — только сопоставляет существующий. Для создания проекта в ProfyPlan нужен отдельный сценарий.

### 4.4 Номенклатура, контрагент, подразделение, ресурс

Использовать существующие поля:

- номенклатура: `name`, `code`, `article`, `unit`, `ntype`;
- контрагент: `name`, `external_code`, `inn`;
- подразделение: `name`, `code`;
- ресурс: `name`, `external_code`, `resource_type`.

Для всех: `uid` обязателен, `updated_at`/`version` желательны.

## 5. Заказы (`kind: orders`)

### 5.1 Обязательное поле типа

Добавить в каждую сущность `orders`:

```json
"order_type": "production_order"
```

Допустимые значения на первом этапе:

- `production_order`.

Зарезервировать на будущее:

- `work_order` (заказ-наряд);
- `supplier_order`;
- `transfer_order`.

Если тип не `production_order`, ProfyPlan не должен создавать производственный заказ. Неизвестный тип — ошибка пакета.

### 5.2 Поля заказа на производство

| Поле | Обязательное | Комментарий |
|---|---|---|
| `uid` | да | GUID |
| `number` | да | номер 1С |
| `parent_uid` | нет | дерево заказов |
| `project_uid` / `project_ext_id` | нет | привязка к проекту |
| `organization_uid` | **да** для внешнего заказа | организация |
| `quantity` | да | количество |
| `unit` | да | единица |
| `start_date`, `due_date` | нет | плановые даты |
| `specification_name`, `product_name` | нет | продукция/спецификация |
| `client` | нет | контрагент |
| `priority` | нет | приоритет |
| `status` | да | статус 1С |
| `updated_at`, `version` | да | для конфликтов |

Требования:

- заказ без организации импортируется как черновик с ошибкой поля и не участвует в расчёте;
- операции, маршрут и этапы передаются отдельным пакетом `routes`, а не внутри `orders`;
- заказ-наряд, заказ поставщику и перемещение **не отправлять** в `orders` без `order_type`.

## 6. Документы (будущие пакеты)

До реализации этих пакетов 1С не должна присылать их в `orders`.

### 6.1 Заказ-наряд (`work_order`)

- `uid`, `number`, `parent_order_uid`;
- `operation_uid` или `route_uid`;
- `executor_uid`/`resource_uid`;
- `planned_quantity`, `planned_hours`;
- `start_date`, `finish_date`;
- `status`;
- `updated_at`, `version`.

### 6.2 Заказ поставщику (`supplier_order`)

- `uid`, `number`, `organization_uid`, `project_uid`;
- `supplier_uid`;
- `warehouse_uid`;
- строки: `nomenclature_uid`, `quantity`, `unit`;
- `planned_date`, `status`;
- `updated_at`, `version`.

### 6.3 Заказ на перемещение (`transfer_order`)

- `uid`, `number`, `organization_uid`;
- `project_uid` — **обязателен**;
- `from_warehouse_uid`, `to_warehouse_uid`;
- строки: `nomenclature_uid`, `quantity`, `unit`;
- `planned_date`, `actual_date`, `status`;
- `updated_at`, `version`.

## 7. Маршруты и состав (`kind: routes` / `bom`)

Для полноценного планирования из 1С нужны отдельные пакеты:

- `routes`: `order_uid`, `route_uid`, `operation_uid`, `stage_uid`, `sequence`, `operation_name`, `resource_uid`, `department_uid`, `duration_hours`;
- `bom`: `parent_nomenclature_uid`, `component_uid`, `quantity`, `unit`, `level`.

Требование: не имитировать операции внутри `plan_snapshot`; план — это результат, а не технологическая структура.

## 8. Факты (`kind: facts`)

Факт — компактное событие, не копия документа.

| Тип | Обязательные поля |
|---|---|
| `production` | `uid`, `order_uid`, `operation_uid`/`stage_uid`, `quantity`, `date`, `status` |
| `order_naryad_close` | `uid`, `order_uid`, `operation_uid`, `executor_uid`, `hours`, `quantity`, `date`, `status` |
| `receipt` | `uid`, `supplier_order_uid`, `nomenclature_uid`, `quantity`, `warehouse_uid`, `date`, `status` |
| `transfer` | `uid`, `transfer_order_uid`, `from_warehouse_uid`, `to_warehouse_uid`, `nomenclature_uid`, `quantity`, `date`, `status` |

Для всех фактов:

- `source_document_uid`, `source_row_uid`;
- `updated_at`, `version`;
- отмена/сторно передаётся как `status=cancelled`, а не удалением без следа;
- изменение факта поднимает ревизию проекта и индикатор «нужен пересчёт».

## 9. События и задания (после пилота)

### 9.1 «Событие: Запись»

Если документ является записью на услугу/приём, использовать `kind: bookings`:

- `uid`, `resource_uid`, `service_uid`, `client_uid`;
- `start`, `finish`, `status`;
- `project_uid` — нет.
- **Не** отправлять в `resource_events`: это не ремонт и не изменение мощности.

### 9.2 «Задание на работу» и «Учёт времени»

- `kind: work_tasks`: `uid`, `project_uid`, `order_uid`, `operation_uid`, `resource_uid`/`executor_uid`, `planned_hours`, `start`, `finish`, `status`.
- `kind: time_entries`: `uid`, `work_task_uid`, `date`, `hours`, `executor_uid`, `source_row_uid`.

Эти пакеты не входят в MVP и включаются настройкой «Учитывать в планировании».

## 10. План из ProfyPlan (`kind: plan_snapshot`)

Оставить текущий контракт. 1С использует:

- `order_ext_uid` — главный ключ заказа;
- `order_ext_id` — резервный номер;
- `resource_ext_uid`, `resource_ext_id`, `resource_name`;
- `start`, `finish`, `resource_load`.

1С не использует и не должна требовать:

- `operation_uid`, `department_uid`, `quantity`, `unit`, `is_critical`.

`plan_snapshot` — снимок; повторная отправка не должна дублировать строки.

## 11. Обновления, конфликты и идемпотентность

1. `uid` — главный ключ; номер/код — резервный.
2. `updated_at`/`version` — для определения изменений.
3. Удаление/отмена — отдельный `op`, не отсутствие объекта в пакете.
4. Повторный `packet_id` не должен применяться дважды.
5. При конфликте «обе стороны изменили одно поле» ProfyPlan создаёт запись конфликта; 1С не должна присылать автоматическую перезапись без версии.
6. Если 1С не может передать версию, минимум `updated_at` и `source_document_uid`.

## 12. Критерии приёмки

- `schemas` и обязательные поля валидируются; неизвестный тип не создаёт сущность.
- Организация и склад создаются/сопоставляются по UID; склад без подразделения не блокирует импорт.
- Дерево проектов и заказов строится по `parent_uid`.
- Заказ на производство без организации не участвует в расчёте и помечается ошибкой.
- Заказ-наряд/поставщику/перемещение не попадают в `ProductionOrder`.
- Факты обновляются по UID, отмена отражается статусом.
- Изменение факта/планового документа поднимает ревизию проекта.
- Повторный пакет не создаёт дублей.
- План из ProfyPlan применяется только к существующему заказу; неизвестные строки пропускаются с журналом.

## 13. Что не входит

- Полный двусторонний документооборот.
- Создание бухгалтерских документов в 1С из ProfyPlan.
- Передача проводок, налогов, оплат и остатков.
- Копирование полных документов 1С.
- Автоматическое включение записей на услуги и заданий в план без настройки.
