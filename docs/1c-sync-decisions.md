# Решения по синхронизации 1С ↔ ProfyPlan

**Дата:** 24.10.2026  
**Статус:** для MVP согласован только режим «1С — ведущая система»; «Совместное планирование» отложено до эксплуатации. Production не обновлён.

## 1. Имена сущностей

Используем две основные колонки и служебный признак:

| Поле | Смысл |
|---|---|
| `name` | рабочее имя в ProfyPlan; его видит и может менять пользователь |
| `external_name` | текущее имя во внешней системе; только для чтения, обновляется импортом |
| `external_name_ack` | имя из внешней системы, которое пользователь уже принял или отклонил |
| `name_overridden` | пользователь закрепил локальное имя |
| `external_name_rev` | версия/время изменения имени в источнике, если 1С её передаёт |

### Правила

1. Новая сущность из 1С: `name = external_name`, `ack = external_name`, `overridden = false`.
2. Имя в 1С изменилось, локальное не переопределено: `name` и `ack` обновляются автоматически.
3. Имя в 1С изменилось, локальное переопределено: появляется запись в списке «Изменения из 1С».
4. «Принять имя из 1С»: `name = external_name`, `ack = external_name`, `overridden = false`.
5. «Оставить локальное»: `name` не меняется, `ack = external_name`, `overridden = true`; повторно не показываем.
6. Следующее изменение в 1С снова создаёт запись, потому что `external_name` опять расходится с `ack`.
7. Ручное переименование в ProfyPlan ставит `overridden = true`; в ограниченном режиме обратно в 1С не уходит.

Для заказов и документов номер/дата — ключи 1С; их не переименовываем.

### Где видит пользователь

- Пункт **«Интеграция → Изменения из 1С»** со счётчиком.
- В карточке: «Наименование» (редактируемое), «Наименование в 1С» (read-only), бейдж «Локальное имя» и кнопка «Принять имя из 1С».
- Массовые действия: «Принять все», «Оставить локальные».

В ограниченном режиме отдельных настроек переименования нет: 1С — источник имени, обратная передача отключена.

## 2. Режим «Совместное планирование» (отложен)

**Решение 24.10.2026:** в текущем MVP не реализуем. Сначала проверяем ограниченный режим на реальных пользователях; возвращаемся к совместному планированию в следующих версиях только при подтверждённой необходимости.

Это новое название вместо технического «двусторонний планировочный». Пользователь выбирает в подключении:

| Режим | Что означает |
|---|---|
| **1С — ведущая система** | 1С присылает справочники, заказы и факты; ProfyPlan возвращает только зафиксированный план |
| **Совместное планирование** | 1С остаётся владельцем учётных документов, а ProfyPlan может менять разрешённые планировочные поля и отправлять их в 1С |

Даже в совместном режиме **бухгалтерские документы 1С не создаются из ProfyPlan**. Не копируем проведение, налоги, оплаты и движения.

### Что куда передаётся

| Данные | Направление | Владелец |
|---|---|---|
| Организации, склады, номенклатура, контрагенты, ресурсы | 1С → ProfyPlan | 1С |
| Проекты и дерево проектов | 1С → ProfyPlan, если проект создан в 1С | 1С |
| Заказы на производство и их дерево | 1С → ProfyPlan | 1С |
| Состав, операции и этапы | 1С → ProfyPlan или ProfyPlan → 1С только после отдельного ТЗ | по согласованию |
| Плановые документы: заказ-наряд, заказ поставщику, заказ на перемещение | 1С → ProfyPlan; планировочные поля — по правилам | 1С / совместно |
| Факты: производство, закрытый сдельный наряд, приход, перемещение | 1С → ProfyPlan | 1С |
| Планировочные поля заказа: проект, даты, приоритет, назначения ресурсов | ProfyPlan → 1С в совместном режиме | совместно |
| Зафиксированный план | ProfyPlan → 1С | ProfyPlan |
| Номера, даты, проведение, суммы, налоги, бухгалтерские движения | только 1С | 1С |

### Простое правило

> 1С отвечает за «что это за документ и что фактически произошло». ProfyPlan отвечает за «как это спланировать». В совместном режиме ProfyPlan может поменять только планировочную часть, а не провести документ за 1С.

### Примеры

**Смена проекта у импортированного заказа**

- В режиме «1С — ведущая»: меняется только проект в ProfyPlan; в 1С ничего не уходит.
- В режиме «Совместное планирование»: создаётся исходящее изменение `order.project_changed`; 1С обновляет проект заказа, если документ не проведён или это разрешено настройкой.

**Добавили операцию в заказ**

- Операция остаётся в ProfyPlan.
- В 1С уходит не операция, а строки плана: ресурс, старт, финиш, загрузка.
- Если нужно создавать операции и этапы в 1С — это отдельный контракт и доработка расширения.

**Создали заказ в ProfyPlan**

- По умолчанию он остаётся локальным и в 1С не выгружается.
- В совместном режиме можно включить «Создавать черновик заказа в 1С». Тогда ProfyPlan отправляет черновик, 1С возвращает UID; проведение и реквизиты остаются за 1С.
- Это отключаемая функция, а не поведение по умолчанию.

**Изменился факт производства**

- 1С → ProfyPlan.
- Факт обновляется по UID документа, проект получает бейдж «Есть новые факты — пересчитайте».
- Автоматического пересчёта нет: пользователь сам запускает новый расчёт.

### Конфликты

- У каждой связанной сущности есть версия/время изменения с обеих сторон.
- Если изменилась только одна сторона — применяем по матрице владения.
- Если обе изменили одно и то же поле — создаётся запись в «Конфликты обмена»: «В 1С: … / В ProfyPlan: …», с выбором стороны.
- Проведённые документы 1С не перезаписываются автоматически.
- Все обмены идемпотентны по `packet_id`; повторный пакет не создаёт дубль.

### Что не мигрирует

- бухгалтерские проводки, налоги, оплаты и складские остатки;
- полные копии документов 1С;
- номера и даты документов;
- операции и этапы в 1С — до отдельного решения;
- факты обратно в 1С.

### В интерфейсе

В настройках подключения — один переключатель:

- **«1С — ведущая система»**
- **«Совместное планирование»**

Дополнительные настройки — в свёрнутом блоке «Дополнительно»:

- разрешать создание черновиков заказов в 1С;
- принимать переименования из 1С;
- передавать переименования в 1С и список типов сущностей;
- политика конфликтов.

По умолчанию: **1С — ведущая**, создание заказов в 1С выключено, обратная передача имён выключена.

## 7. После пилота: документы «Событие: Запись», «Задание на работу», «Учёт времени»

**Статус:** отложено до завершения пилота и проверки ограниченного режима.

### «Событие: Запись»

Это **не** `ResourceEvent` (ремонт/простой/изменение мощности). Если по данным 1С это запись на услугу/приём, её нужно моделировать как **`ResourceBooking`**:

- ресурс/врач/кабинет/оборудование;
- услуга;
- клиент/пациент;
- `start`, `finish`;
- статус: план, подтверждена, выполнена, отменена;
- `ext_uid`, `source_document_uid`, `source_row_uid`;
- проект — если услуга относится к проекту.

Такая запись занимает ресурс на интервал, но не меняет его мощность. Включать её в расчёт можно только настройкой **«Учитывать записи на услуги в планировании»**; по умолчанию выключено. Если записи не связаны с производственными ресурсами, импортировать их не нужно.

### «Задание на работу»

Отдельная `WorkTask`, не `Operation`:

- проект;
- заказ на производство и/или операция;
- ресурс или исполнитель;
- плановые даты;
- плановые часы/количество;
- статус;
- `ext_uid`, `ext_id`, `source`.

Импортировать только если задание влияет на загрузку ресурса/исполнителя; иначе оставить за пределами планирования или включить отдельной настройкой.

### «Учёт времени»

Компактный факт `WorkTimeFact`:

- `work_task_id`;
- дата;
- фактические часы;
- исполнитель;
- `source_document_uid`, `source_row_uid`.

Факт обновляется по UID, не копирует бухгалтерский документ. Изменение факта ставит проекту индикатор «Есть новые факты — пересчитайте».

### Что не делать

- Не маппить «Событие: Запись» в `ResourceEvent`.
- Не копировать полные документы 1С.
- Не смешивать `WorkTask` с `Operation`.
- Не импортировать задачи, не влияющие на ресурсы, без настройки.
- Не передавать эти документы обратно в 1С в ограниченном режиме.

### Условия возврата к теме

- Пилот завершён и ограниченный режим стабилен.
- Подтверждены реальные поля документов 1С.
- Понятно, какие ресурсы пересекаются с производственным планированием.
- Есть владелец продукта для настройки «учитывать/не учитывать» записи и задания.

## 8. Итоги 24.10.2026

- MVP: только ограниченный режим, 1С — ведущая.
- Имена: `name`, `external_name`, `external_name_ack`, `name_overridden`; список изменений и подавление повторов.
- Факты: производство, закрытие наряда, приход, перемещение; ревизии и индикатор пересчёта.
- Типы документов: сейчас только `ProductionOrder`; остальные отсутствуют; локальные документы не выгружаются в 1С.
- Блокировка: `1С — строгий` / `1С — планирование`; структура блокируется только после её импорта.
- После пилота: `ResourceBooking` («Событие: Запись»), `WorkTask`, `WorkTimeFact`.

## 9. Статус 25.10.2026

- `orders`: только `production_order`; остальные типы не отправляются до появления моделей.
- `work_order` = `Документ.ЗаказПокупателя` + `ВидыОперацийЗаказПокупателя.ЗаказНаряд`; отдельного документа нет.
- `customer_order` в MVP не вводим.
- Версии — регистр `ПФП_ВерсииОбъектов` с хэшем; `МоментВремени()` не использовать.
- Факты и `recalc_required`; строгая политика `planning` / `strict_1c`; нормо-часы 3 знака.

## 10. Уточнения по контракту 25.10.2026

- `routes` — шаблон по спецификации, не по заказу. `order_uid` не передаётся/игнорируется; нужен `specification_uid`, желательно `product_nomenclature_uid`. `resource_uid` и `department_uid` необязательны; ресурс из заказа в шаблон не подставляется. `duration_hours` — обязательный норматив в десятичных часах.
- Сторно — встречный факт с отрицательным количеством и `status = "reversed"`; исходный факт остаётся `posted`. В расчёте участвуют оба, `cancelled` исключается. `reversed` на исходный факт не ставится.
- Квитанция об ошибках — отдельный `kind: "receipt"` в `plan_to_1c`, имя `receipt_<packet_id>.json`; `DEPENDENCY_CONFLICT` содержит `details.child_uids` / `details.blocking_orders`. В текущей реализации квитанция ещё не формируется — ошибки видны в журнале ProfyPlan и inbox; это ближайший gap пилота.
