# Сопоставление схем обмена ProfyPlan ↔ 1С (по описанию 1С 0.9.0)

Источник со стороны 1С: `РАЗРАБОТКА.md` (расширение 0.9.0) и `СПРАВКА_ОБЛАЧНЫЕ_КАНАЛЫ.md`.

## 1. Конверт

| Поле | 1С | ProfyPlan | Совместимость |
|---|---|---|---|
| `schema` | `profyplan.exchange.v1` | `profyplan.exchange.v1` | да |
| `packet_id` | уникальный ID пакета, ключ идемпотентности | генерируется `uuid4().hex` | да |
| `direction` | `in` / `out` | `in` / `out` | да |
| `kind` | `ping`, `refs`, `orders`, `plan_snapshot` | те же | да |
| `generated_at` | ISO-8601 | ISO-8601 UTC | да |
| `source.system` | `1c_unf` и др. | `profyplan` | да, информационное |
| `meta` | произвольный объект | используется | да |
| `entities` | массив сущностей | массив сущностей | да |

## 2. `refs` — справочники

| Сущность | Поля 1С | Обработка ProfyPlan | Состояние |
|---|---|---|---|
| `nomenclature` | `name`, `code`, `article`, `unit`, `ntype` | создаёт/обновляет по `ext_uid → ext_id/code`; `ntype` маппится | да |
| `counterparty` | `name`, `external_code`, `inn` | ищет по `ext_uid → external_code → ИНН → имени` | да |
| `department` | `name`, `code` | ищет по `ext_uid → code → имени` | да |
| `resource` | `name`, `external_code`, `resource_type` | ищет по `ext_uid → external_code → имени` | исправлено: принимается `external_code` |
| `project` | `name`, `code` | только сопоставляет существующий проект; новые не создаёт | да, по ТЗ |

Новые проекты из 1С не создаются намеренно: проект — сущность ProfyPlan, 1С передаёт только код/имя для сопоставления.

## 3. `orders` — заказы

| Поле | 1С | Профиль ProfyPlan |
|---|---|---|
| `uid` | GUID заказа | ищет заказ по `ext_uid` первым ключом |
| `number` | номер заказа | `ext_id` и резервный ключ |
| `quantity`, `unit` | количество/единица | обновляются у черновика |
| `start_date`, `due_date` | даты | обновляются у черновика |
| `specification_name` | спецификация/продукция | обновляется |
| `client` | контрагент | обновляется |
| `priority` | приоритет | маппится, если передан |
| `project_ext_id`, `project_name` | проект | сопоставляется, но существующая привязка ProfyPlan не перезаписывается |

Правило обновления: заказ из 1С обновляется, только если он в статусе `draft` и ещё не развёрнут (`exploded_at is None`). Согласованный/развёрнутый заказ не перезаписывается. Новый заказ создаётся черновиком.

## 4. `plan_snapshot` — план из ProfyPlan

| Поле `plan_row` | 1С использует | ProfyPlan передаёт |
|---|---|---|
| `order_ext_uid` | главный ключ заказа | да |
| `order_ext_id` | резервный ключ | да |
| `resource_ext_uid` | главный ключ ресурса | да |
| `resource_ext_id` | резервный ключ (внешний код) | да |
| `resource_name` | последний резерв | да |
| `resource_load` | загрузка ресурса | `1` в v1 |
| `start`, `finish` | интервал | ISO-8601 без пояса, шкала МСК |
| `operation_*`, `department_*`, `quantity`, `unit`, `is_critical` | не используются | передаются для диагностики/будущих срезов |
| `order_uuid`, `resource_uuid`, `operation_uuid` | внутренние UUID ProfyPlan, не используются | передаются |

`plan_snapshot` — это снимок: 1С заменяет строки `РесурсыПредприятия` заказа. Операции, подразделения и количество в 1С из плана не переносятся; переносятся ресурс, загрузка, старт и финиш.

## 5. Ключи трансляции

Отдельной таблицы соответствий нет: ключи хранятся в самих сущностях:

- `ext_uid` — GUID 1С, главный ключ;
- `ext_id` / `external_code` — номер/код, резервный ключ;
- `PlanSnapshotRow` хранит `order_ext_uid`, `order_ext_id`, `resource_ext_uid`, `resource_ext_id` для обратной передачи.

Порядок сопоставления: `ext_uid → external_code/ext_id → имя`. Исправлено для заказов (раньше заказ искался только по номеру), ресурсов и проектов (принимается `external_code`/`code`).

## 6. Что происходит при локальных изменениях в ProfyPlan

| Действие | Сейчас |
|---|---|
| Добавить операцию в импортированный заказ | Операция остаётся локальной. В `plan_snapshot` попадут её ресурс/время, но саму операцию 1С не создаёт. Если заказ не зафиксирован — в 1С ничего не уходит. |
| Сменить проект у импортированного заказа | Меняется только `project_id` ProfyPlan. В `plan_snapshot` проекта нет; 1С проект не обновляет. При следующем импорте существующая привязка не перезаписывается. |
| Переименовать импортированный проект | Локальное имя сохраняется. `refs` из 1С не обновляет имя проекта; если у проекта нет `ext_uid` и имя изменилось, сопоставление по имени может не найти его. |
| Создать проект/подпроект и заказ в ProfyPlan | В 1С не выгружается. У нового заказа нет `ext_uid`/`ext_id` 1С, поэтому `plan_row` не сможет сопоставиться. |
| Изменить справочник (номенклатуру, контрагента, ресурс, подразделение) | Следующий импорт `refs` из 1С перезапишет имя/поля по данных 1С. |
| Изменить заказ после развёртывания/согласования | Импорт из 1С его уже не перезаписывает; локальные изменения остаются в ProfyPlan. |

## 7. Открытые вопросы и предлагаемые правила

1. **Мастер-система.** Для `refs` и `orders` мастер — 1С; для операций, ресурсов внутри заказа и планирования — ProfyPlan. Это нужно зафиксировать в продуктовой инструкции.
2. **Локальные проекты и заказы.** Если их нужно передавать в 1С, требуется отдельный outbound-пакет `refs/orders` и внешний ключ; сейчас такого канала нет.
3. **Смена проекта у заказа.** Нужно решить: запрещать локальную смену для импортированных заказов, писать её в 1С отдельным пакетом или считать локальным переопределением.
4. **Идемпотентность ProfyPlan.** `process_incoming` принимает пакеты без проверки уже обработанного `packet_id`; 1С ведёт такой регистр. Стоит добавить дедупликацию на стороне ProfyPlan.
5. **`project_ext_uid` в `plan_row`.** Если 1С когда-нибудь будет обновлять проект по плану, поле нужно добавить; текущая версия 1С его не использует.
