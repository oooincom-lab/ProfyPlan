# ТЗ 1.4 для 1С AI: доработка расширения после 0.9.0

**Дата:** 24.10.2026  
**Адресат:** разработчик расширения 1С  
**Основание:** `РАЗРАБОТКА.md` (состояние 0.9.0), решения ProfyPlan от 24.10.2026

## 1. Что уже сделано в 0.9.0 и не нужно переделывать

В расширении уже есть:

- файловый обмен, FTP и почта;
- Яндекс Диск и Google Drive;
- OAuth-подключение каналов;
- канонические папки `1c_to_plan`, `plan_to_1c`, `processed`, `archive`, `_state`;
- формирование `refs`, `orders`, `ping`;
- приём `plan_snapshot` и запись ресурсов в заказ;
- архив ошибочных файлов;
- отдельные настройки для Яндекс/Google.

Сохраняем это. Не меняем формат `plan_snapshot`, имена канонических папок и логику файлового обмена. Все новые требования ниже — **дополнение**, обратно совместимое с `profyplan.exchange.v1`.

## 2. Главное правило обмена

**1С — ведущая система** для справочников, заказов, плановых документов и фактов. ProfyPlan:

- принимает данные;
- планирует;
- возвращает только зафиксированный план;
- не создаёт бухгалтерские документы в 1С;
- не отправляет в 1С локальные проекты, заказы, операции и задания.

Двусторонний обмен документами в MVP **не делаем**. Поэтому в 1С не нужно добавлять создание сущностей из ProfyPlan, кроме приёма `plan_snapshot`.

## 3. Общие поля всех сущностей

Для каждого объекта в `entities` добавить:

```json
{
  "type": "...",
  "uid": "GUID 1С",
  "op": "upsert",
  "fields": {},
  "updated_at": "2026-10-24T12:00:00",
  "version": 12
}
```

Требования:

- `uid` — стабильный GUID; не меняется при переименовании/смене номера;
- `updated_at` — **время смены версии в регистре `ПФП_ВерсииОбъектов`**, а не дата документа и не `МоментВремени()`;
- `version` — увеличивается только когда изменился хэш экспортируемых полей;
- `op`: `upsert`, `delete`, `cancel`;
- повторный `packet_id` не должен применяться повторно;
- неизвестный `type`/`kind` — ошибка пакета, а не создание «похожей» сущности.

### 3.1. Версии объектов

`МоментВремени()` не использовать: это дата документа плюс ссылка, а не время последнего изменения.

Рекомендуемая схема — регистр сведений **`ПФП_ВерсииОбъектов`**:

| Поле | Назначение |
|---|---|
| `ТипОбъекта` | тип сущности 1С |
| `Идентификатор` | GUID объекта |
| `Версия` | целое, растёт только при изменении |
| `ДатаВерсии` | время фиксации новой версии |
| `Хэш` | хэш канонического набора экспортируемых полей |

Алгоритм при выгрузке:

1. Собрать канонический набор полей и строк дочерних таблиц.
2. Посчитать хэш (стабильный порядок, ссылки как UID, без представлений).
3. Если записи нет — `Версия = 1`, `ДатаВерсии = now`, сохранить хэш.
4. Если хэш совпал — версию и дату не менять.
5. Если хэш изменился — `Версия += 1`, `ДатаВерсии = now`, сохранить новый хэш.

В пакет передавать `version` и `updated_at = ДатаВерсии`. Это позволяет отличать реальное изменение от простой повторной выгрузки. Удаление/отмена передаются через `op=delete`/`status=cancelled`, а не через отсутствие объекта.

## 4. Справочники

### 4.1 Организации — новый тип `organization`

Сейчас организации в ProfyPlan есть, но без связи с 1С. Добавить в `refs`:

- `uid`;
- `name`, `full_name`;
- `inn`, `kpp`, `ogrn`;
- `is_default`, `is_active`;
- `updated_at`, `version`.

### 4.2 Склады — новый тип `warehouse`

- `uid`;
- `name`, `code`;
- `organization_uid` — если склад привязан к организации;
- `department_uid` — **необязательное**; в 1С группа склада может отсутствовать;
- `is_active`;
- `updated_at`, `version`.

Если `department_uid` нет, ProfyPlan создаёт склад с пустым подразделением и признаком «требует привязки». **Не блокировать импорт склада.**

### 4.3 Проекты и дерево

Сейчас ProfyPlan только сопоставляет проекты, но для загрузки деревьев нужно:

- передавать проекты в `refs` с `parent_uid`;
- разрешить создание проекта в ProfyPlan по `uid` (изменение поведения);
- обновлять имя/родителя при изменении в 1С;
- локальные проекты ProfyPlan в 1С не отправлять.

Поля: `uid`, `name`, `code`, `parent_uid`, `organization_uid` (опционально), `is_active`, `updated_at`, `version`.

### 4.4 Существующие справочники

Оставить и дополнить `updated_at`/`version`:

- номенклатура: `name`, `code`, `article`, `unit`, `ntype`;
- контрагент: `name`, `external_code`, `inn`;
- подразделение: `name`, `code`;
- ресурс: `name`, `external_code`, `resource_type`.

## 5. Заказы и типы документов

Сейчас в `orders` нет типа, и ProfyPlan создаёт из любого элемента `ProductionOrder`. Это нужно исправить.

### 5.1 Обязательное поле `order_type`

Добавить в каждый элемент `orders`:

- `production_order` — заказ на производство (сейчас);
- `work_order` — заказ-наряд (следующий этап);
- `supplier_order` — заказ поставщику (следующий этап);
- `transfer_order` — заказ на перемещение (следующий этап).

**Важно по объектам конфигурации:** `work_order` — это **не отдельный `Документ.ЗаказНаряд`**. В 1С:УНФ это `Документ.ЗаказПокупателя` с `ВидОперации = ВидыОперацийЗаказПокупателя.ЗаказНаряд` и формой `ФормаЗаказНаряда`. Обычный заказ покупателя — тот же объект с другим видом операции; если его понадобится передавать, использовать отдельный `customer_order`, не `work_order`.

Фильтр для 1С AI:

```bsl
Если Документ.ВидОперации = Перечисления.ВидыОперацийЗаказПокупателя.ЗаказНаряд Тогда
    ТипЗаказа = "work_order";
Иначе
    // В MVP обычный заказ покупателя не выгружаем.
    ТипЗаказа = Неопределено;
КонецЕсли;
```

`customer_order` в текущий MVP **не входит**: обычный заказ покупателя — продажа, у него нет состава и операций; планировать в нём нечего. Вернуться к нему можно отдельным этапом «планирование от спроса».

Пока остальные типы не поддержаны в ProfyPlan, 1С **не должна** отправлять их в `orders`. Если отправляет — ProfyPlan фиксирует ошибку и не создаёт производственный заказ.

### 5.2 Дерево заказов

Добавить `parent_uid`. Производственный заказ может быть листовым или дочерним; ProfyPlan хранит `parent_order_id`.

### 5.3 Обязательные поля

- `organization_uid` — обязательна для внешнего заказа;
- `number` — номер 1С;
- `quantity`, `unit`;
- `project_uid`/`project_ext_id`;
- `start_date`, `due_date`;
- `specification_name`, `product_name`;
- `client`;
- `priority`;
- `status`;
- `updated_at`, `version`.

Заказ без организации импортируется черновиком с ошибкой поля и не участвует в расчёте.

`priority` приходит строкой перечисления `ПФП_ПриоритетЗаказа`: `Низкий`, `Обычный`, `Высокий`, `Критический`. Числовой шкалы в протоколе нет. Для отчётов использовать ранг `Низкий=1, Обычный=2, Высокий=3, Критический=4`; обратной трактовки нет.

## 6. Состав, операции и этапы

Добавить отдельные пакеты, не вкладывать их в `orders`:

- `kind: bom` — состав изделия: `parent_nomenclature_uid`, `component_uid`, `quantity`, `unit`, `level`;
- `kind: routes` — маршрут: `order_uid`, `route_uid`, `operation_uid`, `stage_uid`, `sequence`, `operation_name`, `resource_uid`, `department_uid`, `duration_hours`.

Это нужно для планирования операций и этапов. Если в текущей версии 1С этих данных нет, пакет можно отложить, но `order_type` и справочники всё равно нужны.

## 7. Факты

Факты — компактные события, **не полные документы 1С**. Добавить `kind: facts`:

| `fact_type` | Поля |
|---|---|
| `production` | `uid`, `order_uid`, `operation_uid`/`stage_uid`, `quantity`, `date`, `status` |
| `order_naryad_close` | `uid`, `order_uid`, `operation_uid`, `executor_uid`, `hours`, `quantity`, `date`, `status` |
| `receipt` | `uid`, `supplier_order_uid`, `nomenclature_uid`, `quantity`, `warehouse_uid`, `date`, `status` |
| `transfer` | `uid`, `transfer_order_uid`, `from_warehouse_uid`, `to_warehouse_uid`, `nomenclature_uid`, `quantity`, `date`, `status` |

Для всех:

- `source_document_uid`, `source_row_uid`;
- `updated_at`, `version`;
- отмена — `status=cancelled`, не удаление без следа;
- изменение факта поднимает ревизию проекта в ProfyPlan.

## 8. Канонические папки и архив

Оставить существующую структуру:

```
<корень>/1c_to_plan
<корень>/plan_to_1c
<корень>/processed/1c_to_plan
<корень>/processed/plan_to_1c
<корень>/archive/ГГГГ-ММ
<корень>/_state
```

Требования:

- `archive/ГГГГ-ММ` — месяц в московской шкале;
- существующие папки не переименовывать;
- если корень создаёт 1С, он должен быть расшарен ProfyPlan с правом «Редактор»;
- для Google нужен scope `drive`, иначе ProfyPlan не увидит общую папку.

## 9. План из ProfyPlan

`plan_snapshot` не меняем. 1С по-прежнему использует:

- `order_ext_uid` — главный ключ;
- `order_ext_id` — резервный номер;
- `resource_ext_uid`, `resource_ext_id`, `resource_name`;
- `start`, `finish`, `resource_load`.

1С не должна требовать операции, подразделения, количество и `is_critical` из `plan_snapshot`.

## 10. Что не делать в расширении

- Не отправлять в ProfyPlan полные копии бухгалтерских документов.
- Не создавать в 1С заказы/проекты из ProfyPlan.
- Не добавлять двусторонний обмен документами.
- Не маппить «Событие: Запись» в `resource_events`.
- Не менять формат `plan_snapshot`.
- Не создавать дубли папок.

## 11. После пилота

Отдельно, не в MVP:

- `bookings` — «Событие: Запись» как запись на услугу/приём;
- `work_tasks` — «Задание на работу»;
- `time_entries` — «Учёт времени»;
- `resource_events` — только настоящие события мощности (ремонт, простой, изменение доступности).

## 12. Порядок работ для 1С AI

1. `order_type` и `updated_at`/`version` во всех сущностях.
2. `organization` и `warehouse` в `refs`; `project` с `parent_uid`.
3. `parent_uid` заказов.
4. `facts`: производство, закрытие наряда, приход, перемещение.
5. `bom`/`routes`.
6. Приёмка на реальных пакетах.

## 13. Критерии приёмки

- Пакет без `order_type` не создаёт производственный заказ, если это новый тип.
- Организация и склад сопоставляются по UID; склад без подразделения не блокирует импорт.
- Проекты создаются/обновляются по `uid` и `parent_uid`.
- Заказы строят дерево по `parent_uid`.
- Факты обновляются по UID; отмена отражается статусом.
- Повторный пакет не создаёт дублей.
- План применяется только к существующему заказу; неизвестные строки пропускаются с журналом.
- `archive/ГГГГ-ММ` и канонические папки совпадают на обеих сторонах.

## 15. Уточнения после ответа 1С AI от 24.10.2026

Принято:

- `order_type` обязателен; `work_order`, `supplier_order`, `transfer_order` пока не отправляются в `orders`;
- новые пакеты — отдельные `facts`, `bom`, `routes`;
- `plan_snapshot` не меняется;
- `parent_uid` передаётся; если иерархия в базе выключена, значение `null` допустимо;
- факты подтверждены в объёме §7;
- последовательность: версии/`order_type` → организации/склады → `parent_uid` → факты → `bom`/`routes`.

Требуют подтверждения:

1. ~~Шкала `priority`~~ — подтверждено: строковое перечисление, числа не используются.
2. ~~`organization_uid` в каждом заказе~~ — подтверждено: реквизит обязателен в 1С.
3. ~~Стабильность `project_uid`~~ — подтверждено: GUID не меняется при переименовании.
4. ~~`bom`/`routes`~~ — подтверждено: данные есть, порядок остаётся последним.

Дополнительно подтверждено: у заказа на производство нет реквизита «Родитель»; дерево строится через «Основание» (`ЗаказНаПроизводствоОснование`). `parent_uid` заполняется из «Основания», иначе `null`. Общий `ДокументОснование` в `parent_uid` не попадает, иначе в дерево попадут заказы покупателя/поставщику. 1С передаёт родителей раньше дочерних; при цикле заказ уходит с `parent_uid = null` и записью в журнале.

Уточнение по объектам: `Документ.ЗаказНаряд` как отдельный объект не используется; `work_order` — это `Документ.ЗаказПокупателя` с `ВидОперации = Перечисления.ВидыОперацийЗаказПокупателя.ЗаказНаряд`. Обычный `ЗаказПокупателя` в MVP не выгружается; `customer_order` не вводим.

Версии: `МоментВремени()` не использовать. Принят регистр `ПФП_ВерсииОбъектов` с версией и хэшем экспортируемых полей; версия растёт только при изменении хэша, `updated_at` — время смены версии.

## 16. Нормо-часы

1С передаёт продолжительность в часах десятичным числом с **тремя знаками после запятой** (например, `1.234`). ProfyPlan хранит её как `Decimal` в часах, без промежуточного `float`:

- `operations.duration_base`, `setup_time`, `teardown_time`, `fact_hours` — `numeric(10,3)`;
- `plan_snapshot_rows.duration_hours` — `numeric(14,3)`;
- `catalog_operations.default_duration_hours` — `numeric(8,3)`.

В `plan_snapshot` отдаётся три знака после запятой. Для отображения минуты считаются как `hours * 60`; округление до целых минут выполняется только в UI или итоговом отчёте, не при хранении. Это сохраняет точность при суммировании операций.

## 17. Ответы на вопросы 1С AI

### 17.1 Сотрудники и бригады

- `employee` — **отдельный тип в `refs`**. Поля: `uid`, `name` (ФИО), `code` (табельный), `position`, `department_uid`, `is_active`, `updated_at`, `version`.
- Бригады, отделения и участки — **иерархия подразделений**, а не отдельные справочники. У `department` добавляется `kind`: `brigade` | `division` | `section` | `department`; связь через `parent_uid`.
- `employee.department_uid` указывает на бригаду или подразделение. Если нужна отдельная ссылка на бригаду, она совпадает с `department_uid` записи вида `brigade`; дублировать `brigade_uid` не нужно.
- `executor_uid` в фактах дополняется `executor_type`: `employee` или `brigade`. Для бригады `executor_uid` — UID подразделения с `kind=brigade`.
- Сотрудник **не заменяет ресурс**. Если сотрудник или бригада участвует в ресурсном планировании, ProfyPlan связывает запись с `Resource` (`resource_type=employee/team`). Справочник сотрудников остаётся кадровым, ресурс — мощностным.

### 17.2 Минимальный набор для фактов

| Факт | Обязательные ссылки |
|---|---|
| `production` | `order_uid`, `nomenclature_uid`, `department_uid` или `warehouse_uid`, `organization_uid` |
| `order_naryad_close` | `order_uid`, `operation_uid`, `executor_uid` + `executor_type`, `organization_uid` |
| `receipt` | `supplier_order_uid`, `nomenclature_uid`, `warehouse_uid`, `counterparty_uid` |
| `transfer` | `transfer_order_uid`, `nomenclature_uid`, `from_warehouse_uid`, `to_warehouse_uid` |

### 17.3 Частичный `refs` и порядок

- `refs` может быть частичным. Отсутствие сущности в пакете **не означает удаление** и не должно очищать справочник.
- Удаление — только явный `op=delete`.
- В рамках операции 1С отправляет `refs` до `orders` и `facts`.
- Если заказ или факт всё же пришёл раньше справочника, ProfyPlan **не отбрасывает** его: создаёт черновик/факт с незаполненной ссылкой и ставит в очередь на повторное связывание, когда придёт `refs`. Ошибкой это не считается.
- Для файлового канала 1С добавляет префикс порядка: `01_refs_*`, `02_orders_*`, `03_facts_*`. ProfyPlan также обрабатывает `refs` раньше остальных типов, если файлы пришли одновременно.

### 17.4 Полная выгрузка

- Повторный полный `refs` — обычный upsert; версия растёт только при изменении хэша.
- Полная выгрузка может быть отфильтрована по документам за период; отсутствие остальных сущностей не считается удалением.
- Для настоящего удаления 1С передаёт `op=delete` отдельной сущностью.
- Полная выгрузка не должна сбрасывать локальные проекты, созданные в ProfyPlan.

### 17.5 Ресурсный профиль подразделения

Любое подразделение теоретически может быть ресурсом, но **не каждое подразделение автоматически является ресурсом**.

Разделяем две роли:

- `Employee` / `Department` — организационная единица: кто это и где он находится;
- `Resource` — планировочная ёмкость: сколько работы можно назначить, по какому календарю и с какой мощностью.

`Resource` получает ссылку на субъект:

- `subject_type`: `employee` | `brigade` | `department` | `equipment` | `workplace`;
- `subject_id` / `subject_uid`;
- `parent_id` — иерархия ресурсов;
- `capacity_mode`: `individual` | `pool`;
- `schedule_id`, `capacity_per_unit`, `capacity_unit`;
- `is_bookable`.

Правила:

1. Сотрудник или бригада могут иметь ресурсный профиль, только если они реально участвуют в планировании.
2. Бригада или участок как `pool` имеет суммарную ёмкость; входящие сотрудники не должны одновременно бронироваться отдельными ресурсами на ту же работу.
3. Для операции выбирается **один уровень ресурса**: сотрудник, бригада или участок. Это защищает от двойного бронирования.
4. Ресурсный профиль можно включить/выключить; организационная единица без профиля остаётся справочником.
5. Для агрегированного ресурса состав участников хранится через `ResourceMember`; мощность можно задать вручную или рассчитывать из состава и календарей.
6. Факты и операции ссылаются на `resource_uid`; `executor_uid` остаётся ссылкой на сотрудника/бригаду для кадрового и нарядного учёта.

В 1С AI передаёт `employee` и `department` как справочники; отдельный `resource` — только если в 1С есть рабочий центр/ресурс, который действительно планируется. Если ресурсный профиль создаётся в ProfyPlan, он хранит `subject_uid` и не дублирует имя/код сотрудника или подразделения.
